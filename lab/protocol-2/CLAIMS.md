# Claims

Each of the eight things that must be true, and how it stands: **verified** by a named test in
`test/` (run `npm test`; the network one with `npm run test:net`), or **believed**, with the reason
and what would verify it. Nothing here is shipped.

| # | Claim | Status | Test, or reason |
|---|---|---|---|
| 1 | A person owns their records. Only they, or whoever they allow, can write them. | Verified | `1-owner-writes`: a stranger's well-formed entry, a claimed grant that does not exist, and a re-signed real entry are all refused; a delegate writes only inside its grant (collection, operation, count) and can never grant, revoke or publish keys, whether the client or the host is asked. |
| 1 | Nobody can fake one. | Verified | `1-owner-writes`: one changed byte, one changed field, one dropped entry: every reader refuses. `0-vectors`: the same inputs give the same bytes, so there is no second valid form. |
| 2 | Records live on hosts anyone can run. | Verified | Every test starts hosts from one file over SQLite on a random port; `2-hosts` scans the host's disk: no seed, no signing key, no reader key, no wallet key, in raw, hex, base64 or base64url. |
| 2 | A person can use several and leave any of them freely. | Verified | `2-hosts`: two hosts serve one log; one goes down; writing continues at the other. A host goes dark for good; the log comes back from an index, moves to a third host, the pointer is re-signed, and the index follows. |
| 2 | Hosts cannot fake records. | Verified | `2-hosts`, `3-index-no-directory`: a forged entry written straight into the host's database is refused by a reader verifying the log, by an index, and by a fresh host over the same file. |
| 2 | Hosts cannot read private ones. | Verified | `5-private`, `2-hosts`: the disk and everything the host serves hold none of the plaintext, not even the collection name. What the host sees is stated in `SPEC.md`: size, an opaque key, the readers' key ids, timing. |
| 2 | Hosts cannot hold anyone hostage. | Verified for the data, believed for the DHT part | `2-hosts` (above). Every entry is public bytes or ciphertext, and every index keeps a copy, so a host can withhold service but never the records. A host can refuse to store the pointer; the DHT (`net/pkarr`) and every index take it too. |
| 3 | Anyone can read public records and build an index, with no central directory. | Verified | `3-index-no-directory`: an index told one URL finds a profile on another host through a review's reference and a signed pointer, from the DHT stand-in, from a host that caches pointers, or from another index. Two independent indexes reach the same state. `net/pkarr`: the pointer round-trips through a public Pkarr relay onto the BitTorrent DHT, run by nobody for Forest. |
| 4 | AI assistants can act for a person within limits the person sets. | Verified | `4-delegation`: collection, operation, count, private-or-not, expiry, each refused at its edge. The grant is a public record anyone can read. |
| 4 | Including while the person's phone is off. | Verified | `4-delegation`: after the grant, nothing from the seed exists in the test's scope; the agent writes from its own key, the profile's DID and the grant's CID. |
| 4 | Without ever holding the person's keys. | Verified by construction, shown | The agent's key is random, made where the agent runs; the grant carries only its public DID. `4-delegation` builds the agent from that key alone. Nothing in the protocol has a place to put the person's key. |
| 4 | The person can take that power back at any time. | Verified | `4-delegation`: a revocation entry; every later write under the grant is refused, by any host, honest or not, because revocation is a chain rule. Expiry alone is a clock rule an honest host enforces; the same test shows a host with a stopped clock accepting a backdated entry. |
| 5 | Private records later (contacts, calendar, health, an AI's memory of you) on the same design. | Verified now, at prototype size | `5-private`: the same entry, the same signature, the same log, sync, index and move; a contact, a health record and an AI's memory; read by the owner from the seed on a second device, by the agent after a restart; not by a stranger, not by another agent, not after a byte changes, not after the owner re-addresses the record. |
| 6 | Nothing public links one person's profiles. | Verified for the protocol's own data; believed for behaviour | `6-unlinkable`: two profiles of one seed, on different hosts and sharing one, each with an assistant: every public token 16 characters or longer is compared across everything readable, and none is shared. Not covered: timing, IP addresses at the host, and an app that writes to both at once; those are product rules (jitter, a front, separate sessions), as before. |
| 7 | It scales to billions of people and records. | Believed; measured small | `7-scale`: cost per write is flat across 200 profiles and across 1,000 entries in one log; the index takes 1,000 entries in about 2 s in JavaScript. Nothing is global: one log per profile, one state per profile, no cross-profile structure, so hosts and indexes shard by DID with no coordination. The arithmetic is in `README.md`. Not measured: a host under real load, the DHT at billions of pointers (it need not carry them: hosts and indexes serve pointers first). |
| 8 | One person can audit it in a day. | Verified as a bound; believed as a day | `8-audit`: about 1,300 lines of source in ten files, the rules in one; eight dependencies, each a named standard piece. `SPEC.md` gives a reading order. Whether one person reads it in a day is a judgment; the number says it is possible. |
| — | Use well-reviewed pieces; invent only what nothing existing does well. | Stated | `SPEC.md`, "What is borrowed and what is new". New: the entry's field set and its rules (about 280 lines), the grant's limits, and the name of one DNS record. Everything else is unchanged from a standard. |
| — | The four record shapes need no change. | Verified | `9-shapes`: the example records validate against `shapes/lexicons` with the AT Protocol lexicon library, round-trip byte for byte, and index; a photo travels as a blob. |
| — | A host cannot fork a log; a writer who does is caught. | Verified | `10-fork`. |
| — | Registration, escrow, keys recipe unchanged. | Believed | Not run here. The DID changes form (did:key, 56 characters) and fits the registry's 64-byte bound; the profile's wallet is derived with the recipe's v1 label, so it is the same wallet. `keys/` gains two labels and loses one key; see `README.md`, "What changes". |
